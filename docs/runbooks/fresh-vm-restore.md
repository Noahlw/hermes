# Fresh-VM Restore Runbook (Portable Restore)

**Parent ticket:** [#48 — Portable restore: Drive dumps](https://github.com/Noahlw/hermes/issues/48)

This runbook covers standing up Hermes on a new (or recovered) VM using GitHub clone
and Drive backups. A full second-machine disaster drill is **out of scope** for this
document — this covers the documented restore path only.

---

## Prerequisites

| Requirement | Notes |
|---|---|
| **GitHub access** | Clone this repo. App/config comes from GitHub, not Drive. |
| **Age unlock key file** | The private age identity (`hermes-age-key.txt`) generated by `key-bootstrap.sh`. **Never uploaded to Drive.** You must have this file from the original machine or secure storage. |
| **Drive access** | rclone configured with `gdrive:` remote pointing to the same folder ID (`17yovLP4BK1L_2jJKXbu4H4F-1kiGXzQM`). |
| **Postgres 16** | Hermes DB + codebase index DB on systemd Postgres (`:5433`). |
| **Postgres (Honcho)** | Honcho's Postgres on Docker (`:5432`). |
| **age** | `brew install age` or `apt install age`. |
| **rclone** | Standard install. Remote name defaults to `gdrive:`. |

## Step-by-step restore

### 1. Clone Hermes from GitHub

```bash
git clone https://github.com/Noahlw/hermes.git /home/ubuntu/hermes
cd /home/ubuntu/hermes
```

### 2. Provision Postgres (if fresh VM)

Run the #47 Postgres provision script to set up the Hermes Postgres instance:

```bash
sudo ./scripts/vm/provision-hermes-postgres.sh
```

This creates:
- `hermes` DB on `127.0.0.1:5433` owned by role `hermes_app`
- `codebase_index` DB on `127.0.0.1:5433` owned by role `codebase_index_app`

Honcho's Postgres (`:5432`) is presumed running via Docker Compose.

### 3. Restore databases from Drive

> **Before restoring into production DBs**, consider running the smoke test first
> (see Step 4) to verify backup integrity.

Locate your age identity file and run:

```bash
./scripts/vm/restore_postgres_drive.sh /path/to/hermes-age-key.txt
```

This will:
1. Find the latest daily backup on Drive
2. Download `hermes.dump`, `codebase_index.dump`, `honcho.dump` + `secrets.age`
3. Decrypt secrets with the age key
4. `pg_restore` into production databases (`--clean --if-exists`)

**To restore a specific date:**

```bash
RESTORE_DATE=2026-07-27 ./scripts/vm/restore_postgres_drive.sh /path/to/hermes-age-key.txt
```

**To restore from weekly snapshot:**

```bash
RESTORE_SOURCE=weekly ./scripts/vm/restore_postgres_drive.sh /path/to/hermes-age-key.txt
```

**To preview without modifying databases:**

```bash
./scripts/vm/restore_postgres_drive.sh /path/to/hermes-age-key.txt --dry-run
```

### 4. (Optional) Same-VM restore smoke

Verify backup integrity by restoring into **disposable** databases:

```bash
./scripts/vm/smoke-restore.sh /path/to/hermes-age-key.txt
```

This will:
- Download the latest daily backup
- Decrypt `secrets.age` (proves crypto works)
- Create `hermes_smoke`, `codebase_index_smoke`, `honcho_smoke` databases
- `pg_restore` each dump into its smoke DB
- Run SELECT queries to verify restored data
- Drop smoke databases
- Exit 0 if all checks pass

### 5. Restore runtime secrets

After restore, source the decrypted `.env`:

```bash
source /tmp/restore-*/secrets/.env   # or wherever the restore script extracted
```

Copy or symlink to `~/.hermes/.env`:

```bash
cp /tmp/restore-*/secrets/.env /home/ubuntu/.hermes/.env
```

If rclone config was restored:

```bash
cp /tmp/restore-*/secrets/rclone.conf ~/.config/rclone/rclone.conf
```

### 6. Bring up Hermes services

```bash
# Restart Hermes gateway
sudo systemctl restart hermes-gateway.service

# Restart Hermes indexer
sudo systemctl restart hermes-indexer-webhook.service
sudo systemctl restart hermes-indexer-reconcile.timer
```

### 7. Re-fetch repo working trees

Repos are re-fetched from the GitHub allowlist. Run the indexer's reconcile
or trigger a first-index per allowlisted repo:

```bash
# List configured repos
python -m hermes.indexer list-repos

# Re-index each
python -m hermes.indexer first-index owner/repo
```

### 8. Register backup cron (enables ongoing backups)

Add/update the cron entry in hermes-agent's `cron/jobs.json`:

```bash
# Edit /home/ubuntu/.hermes/cron/jobs.json and add:
# {
#   "id": "portable-postgres-backup",
#   "name": "Portable Postgres backup to Drive",
#   "enabled": true,
#   "command": "/home/ubuntu/.hermes/scripts/vm/backup_postgres_drive.sh",
#   "schedule": "0 5 * * *",
#   "log_file": "/home/ubuntu/.hermes/logs/cron/portable-postgres-backup.log"
# }
```

Restart hermes-gateway to pick up changes:

```bash
sudo systemctl restart hermes-gateway.service
```

A template cron config is available in this repo at `cron/jobs.json`.

## Verification checklist

After a full restore, verify:

- [ ] Hermes gateway is running and accepting connections
- [ ] `psql` can connect to `hermes` DB and SELECT from `audit_events`
- [ ] `psql` can connect to `codebase_index` DB and SELECT from `repos`
- [ ] Honcho Postgres is running and Honcho sessions are intact
- [ ] Runtime `.env` is sourced and Hermes services recognize tokens
- [ ] rclone can access `gdrive:` remote
- [ ] Repo working trees are checked out and current
- [ ] Backup cron is enabled and runs on schedule

## Key files reference

| File | Purpose |
|---|---|
| `scripts/vm/key-bootstrap.sh` | Generate age key + initial secrets upload (#50) |
| `scripts/vm/encrypt-secrets.sh` | Re-encrypt and upload updated secrets |
| `scripts/vm/backup_postgres_drive.sh` | Daily (or weekly) pg_dump + upload + prune (#51, #52) |
| `scripts/vm/restore_postgres_drive.sh` | Download, decrypt, pg_restore (#54) |
| `scripts/vm/smoke-restore.sh` | Same-VM restore smoke into disposable DBs (#54) |
| `cron/jobs.json` | Hermes cron template with portable-backup entry (#53) |

## Out of scope

- Full second-machine disaster drill (separate follow-up).
- Cross-provider replication / multi-region HA.
- Backing up SSH host keys or full `/home/ubuntu/` directory.
- Automated repo working tree re-fetch (manual by design — repos come from GitHub, not Drive).
